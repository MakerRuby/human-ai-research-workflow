# 工作流程

## 目标先落在交付物上

先用一段话明确“为谁解决什么问题，最后凭什么判断已完成”。区分用户期望、已知事实、暂用假设和未决问题。把模糊词转成可以查看的对象：例如“投稿前准备完成”应对应定稿正文、图表与源文件、补充材料、报告清单、来源与代码说明、作者待确认项等；期刊接收不属于可控制的完成条件。

近期按“目标 → 交付物 → 工作包 → 执行动作”展开。跨阶段项目可加里程碑和子系统，但不强制六层目录。每个工作包有一个主要产物、输入版本、完成判据、依赖、负责人和下一动作。若一项任务需要多次互不相关的验收，或失败后难以定位原因，再拆分。不要把所有远期动作一次性排满。

## 先做能推翻路径的小检查

列出最可能导致项目无效或大返工的假设，依次问：

1. 如果此假设不成立，哪些工作会失去意义？
2. 什么最小证据能区分继续、改路与终止？
3. 最多投入多少时间、算力、费用？什么结果触发转向？

示例：先实际读取候选数据的小样本，验证结局、暴露、独立样本量和来源关系，再投入完整建模。不能以数据库介绍页或论文中的一句话替代可访问文件的核实。探针失败是有效产出，记录排除原因，避免换个会话重复尝试。

## 权限与决定

| 情况 | 动作 |
|---|---|
| 范围内、可逆、已有约定的执行细节 | 直接做，必要时记录假设 |
| 信息不全但不影响其他工作 | 标出待决项，推进独立任务 |
| 会改变科学问题、主要终点、验证设计或重要资源承诺 | 提出具体备选、代价与建议，提交约定责任人决定 |
| 外部发布、提交、付费、破坏性操作或新数据外传 | 依据用户已有授权；没有授权时先完成可审查材料，再询问 |

不把“需要记录”误解为“每次需要批准”。设置项目约定的授权范围，而非逐行批准操作。用户明确的决定优先于模板默认值，但不能把不存在的科学证据记成存在。

## 执行周期

每一轮选择最能推进交付或消除风险的少量任务。开始前确认输入可用、判据明确、执行权限够用；不满足时先补充条件。执行后保存结果、相关输入和方法版本，再做适用的检查。发现问题时先定位影响范围，改正后重查受影响部分，避免无理由地全量重跑。

批量出图、批量清洗、批量文档等任务先选代表件和边界件。目的在于验证共用规则；样例足以检验且已获授权后继续批量执行，不增加普遍的人类放行关口。

进度更新围绕“完成了什么、依据是什么、哪项不确定性还存在、下一步解决什么”。在关键里程碑、交接、结束会话或重要改变后更新持久记录，不为每个微小操作写报告。不要同时维护多份相同任务状态。

## 续接与返工诊断

续接读取入口和状态页后，仅加载本轮所需方案、任务、版本和决定。先检查标记为完成的关键输入是否存在、是否与当前版本一致。状态过时应修复记录，不要求用户重新描述全部历史。

返工时区分目标改变、输入变化、方法错误、实现错误、验收遗漏和表达问题。沿依赖回溯到最早失效处，保留有效上游，只重做受影响下游。记录一项可执行修正即可；不要因一次局部错误不断增加全项目规则。

## 收尾

交付时列明可打开的产物、检查结论和适用范围、尚未完成的必要项。将“草稿完成”“检查完成”“负责人接受”分开。科研项目的开放问题、负结果和局限也是成果的一部分。最后保留明确的下一动作或终止理由，不用“基本完成”掩盖缺口。
