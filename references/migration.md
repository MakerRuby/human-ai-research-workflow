# 原包适配与迁移

## 从 v3 升级到 v4

v4 不改变状态结构版本（仍为 2），新加的集合和字段都是可选的，v3 项目不迁移也能继续通过检查。按需逐步采用：

1. 研究项目可在 `project-state.json` 中补上 `"questions": []` 和 `"hypotheses": []`，并按模板新建 `HYPOTHESES.md`、`SEARCH_LOG.md`、`NARRATIVE.md`。初始化器不会覆盖已有文件，可以用它只补缺失的模板。
2. 已有的研究问题登记为 `Q-*`。澄清度按当前实际情况如实填写，不倒推历史。
3. 进入问题树之后，新任务挂上 `serves`；旧任务不强制补。
4. 已做过的检索，能还原检索式和日期的就补登到检索日志；还原不了的不补，后续检索照常登记。
5. 用 `project.designs` 标注研究类型；需要伦理或注册关口时，手工加入 `E1` 或 `R1`，并写明依赖关系。

## 升级到 v3

v3 保留基础检查，增加通用宿主适配、目录导航、治理闭环、实际运行与比较、只读审阅、固定包及退出使用。保留旧包和旧项目原件；本包不自动安装或覆盖旧技能。

1. 备份权威状态，识别既有事实源与当前路径；不要因缺 README 就重建项目。
2. 若采用新脚本，显式审阅状态迁移：schema_version 改为 2，补 layout 与新集合空数组，保留 artifacts/checks/tasks/gates 编号和原路径。初始化器不会替你迁移已有状态。
3. 仅将有实际依据的历史记录迁入；旧 PASS 不自动等于当前 accepted、完整复现或负责人批准。缺证据保持待补，不编造历史。
4. 按下一任务逐步补齐发现、变更、复现和审阅。不强制补写全部旧过程，也不将原方法悄悄改写成预先计划。
5. 先运行只读检查，再开展授权内工作。schema1 能读不代表扩展治理已验收；新运行、归档和交付脚本要求 schema2。
6. 保留项目根既有 README 和规则，合并导航增量。layout 可调整业务目录，管理状态路径仍固定 `_pm/project-state.json`；不自动搬文件。

下文是原包到 v2 的历史修正及仍适用的原则。

## 保留的机制

目标到交付物再到任务与依赖的分解；近期详细、远期粗略的滚动规划；高不确定性先验证；首件与边界检查；数字来源；跨会话状态；任务包与变更记录。这些机制按项目风险和用户偏好使用。

## 本次修正

| 原包规则或实现 | v2 处理及原因 |
|---|---|
| 全部验收最终都应脚本 PASS/FAIL | 增加专业评审和待验证状态，防止格式通过被误当科学成立 |
| 任意两种合理方案都停下来问人 | 可逆实施细节自主；科学取舍、目标冲突与权限变化才升级 |
| 新会话或非平凡任务逐次等“执行” | 保留既有授权；先核对记录，再继续授权内工作 |
| 所有 N>1 批量都人工首件放行 | 按风险选择代表件和边界件；授权范围内通过检查后可继续 |
| AI 不能检查自己的产物 | 要求真实检查；高风险结论另用不同证据或合格评审，不否定执行者自检 |
| 固定种子、版本即可保证幂等或逐字节相同 | 分清重跑、可重复性、幂等；依任务设置容差和环境约束 |
| 四类返工被断言为唯一因果链 | 按实际根因与影响诊断，明确也可能相互独立 |
| 固定规划比例、覆盖比例和返工倍数 | 删除未经证据支持的普遍数字；用项目实测调整投入 |
| 状态页承载全部事实 | 状态页作索引，范围、方案、参数、版本与证据各有归属 |
| S 声称不写文件，脚本仍生成 CORE | S 在脚本中明确不创建目录和文件 |
| M 级描述与实际生成的 WBS/CHANGELOG 不一致 | 脚本清单与入口说明一致，额外记录按需加入 |
| 模板强设 Python 版本、阈值、图件规格 | 未确认参数为 null；规格按真实项目填写 |
| `--force` 可直接覆盖，缺模板只警告继续 | 不提供覆盖参数；写前全量检查模板和目的路径 |
| 简单替换会破坏含冒号或引号的 YAML 值 | 新项目用标准库生成 JSON 配置；既有 YAML 保留 |
| 缺少专项技能交接和科研阶段流程 | 增加能力发现、任务接口、集成检查及研究流程 |

## 现有项目采用方式

1. 先读现有入口、任务、配置、方案和成果。列出当前有效记录及冲突，识别谁维护哪类事实。
2. 保留项目现有 `_pm/config.yaml`、目录与任务编号。v2 初始化检测到既有 YAML 时沿用路径，不再生成第二份配置。其他既有等价格式也优先适配，不强制转换。
3. 不直接覆盖 `AI_CONTRACT.md`；提出具体差异，按既有授权做有记录的合并。既有已验收结论不能因旧文档有“PASS”就直接导入新状态。
4. 新记录先从当前阶段和下一个交付物开始，不追求一次补齐全部历史。无法重建的历史标为证据缺失。
5. 如使用检查脚本，建立 `_pm/project-state.json` 的版本与依赖索引。旧成果可先登记为 `produced` 或 `checked`；有对应实际检查与必要评审后才登记 `accepted`。
6. 迁移前记录需要保护的文件，迁移后核对内容未意外丢失。初始化器只补缺，不替代人工合并和科学审查。

历史 v2 使用独立目录 `ai-project-blueprint-v2`；v3 最初以 `ai-project-blueprint-v3` 发布，现统一命名为 `human-ai-research-workflow`。本节描述的是 3.0.0 的历史改名，不限定当前技能版本。新名称不改变已有项目的状态结构和文件职责，不需要为改技能名称搬迁研究文件。替换技能时避免让两个旧新入口同时处理同一项目。本包不自动安装、替换原技能或创建新会话。
